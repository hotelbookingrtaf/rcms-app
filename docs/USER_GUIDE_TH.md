# คู่มือการใช้งาน RCMS v1.3 (Prototype)

## 1. เข้าสู่ระบบ

เปิด Web App แล้วกรอกบัญชีทดสอบที่แสดงใต้ฟอร์มล็อกอิน บทบาทจะกำหนดเมนูและปุ่มที่ใช้งานได้ ระบบต้นแบบยังเก็บบัญชีในหน่วยความจำ จึงใช้เพื่อสาธิตเท่านั้น

## 2. แดชบอร์ด

ตรวจจำนวนผู้ประกอบการ ใบแจ้งหนี้ ยอดค้าง งานรออนุมัติ และกราฟมูลค่าจากข้อมูลต้นทาง ตัวเลขกราฟไม่ใช่การคำนวณอัตราค่าไฟ/น้ำใน RCMS

## 3. ผู้ประกอบการ

ใช้ค้นหา เพิ่ม และแก้ข้อมูลผู้ประกอบการ แต่ต้องจำไว้ว่าโครงสร้างจริงคือ Tenant → Site → Service Account → Meter หน้าจอนี้ยังเป็น projection แบบย่อสำหรับ prototype

## 4. นำเข้าหน่วยใช้

1. เลือกบริการ “ค่าไฟฟ้า” หรือ “ค่าประปา”
2. เลือกงวดบิลให้ตรงกับไฟล์
3. กด **Import Excel** และเลือกไฟล์
4. ระบบจำแนก data schema ก่อนอ่านข้อมูล
5. ตรวจจำนวนจับคู่, warning, รายการต้องแก้ และแถวที่ข้าม
6. ตรวจ preview ให้เลขมิเตอร์ เลขจด หน่วยใช้ และจำนวนเงินถูกต้อง

กฎสำคัญ:

- ไฟล์เลขจดต้องมีจำนวนเงินจากระบบต้นทาง
- ผลต่างเลขจดใช้ตรวจความสอดคล้อง ไม่ใช้แทน `usageUnits`
- สีแดงจะถูกกันออกจากการออกใบแจ้งหนี้
- หน่วยศูนย์เดือนแรกเป็นการติดตาม ไม่ใช่ข้อสรุปว่ามิเตอร์เสีย
- ไฟล์ทะเบียนจัดเก็บรายได้จะถูกจำแนกเป็น `REVENUE_LEDGER_V1` และไม่ปนกับ reading import

## 5. ออกใบแจ้งหนี้

1. ตรวจว่า reading ไม่มี RED exception
2. เลือกรูปแบบ Statement รวม/แยก
3. กด **ประมวลผลรอบบิล**
4. ระบบสร้าง financial invoice แยกไฟฟ้าและประปาเสมอ
5. เปิดดู พิมพ์ หรือส่งผ่าน LINE (ใน prototype เป็น mock)

โลโก้จะแสดงที่หัวเอกสารและเป็นลายน้ำจางด้านหลังใบแจ้งหนี้/ใบเสร็จ

## 6. ตรวจการชำระเงิน

ตรวจข้อมูลสลิป ยอด อ้างอิง และ OCR ก่อนยืนยัน ใบแจ้งหนี้ต้องเป็น PAID เฉพาะเมื่อยอด allocation ที่ยัง active ครบ invoice เท่านั้น Prototype ปัจจุบันรองรับการสาธิตยอดเต็ม ส่วน short/overpayment/reversal มี rule และ fixture แล้ว แต่ต้องย้ายไป transactional API ก่อนใช้จริง

## 7. การระงับและต่อบริการ

1. เจ้าหน้าที่รายได้สร้างคำขอแยก “ไฟฟ้า” หรือ “น้ำ”
2. Supervisor/Admin อนุมัติหรือปฏิเสธ
3. การอนุมัติยังไม่เปลี่ยนสถานะบริการ
4. Utility Field Officer/Admin ลงพื้นที่และปิดใบงาน
5. ระบบจึงเปลี่ยนสถานะเฉพาะ Service Account ที่อยู่ในใบงาน

## 8. รายงาน ประวัติ และ Audit

- ประวัติการชำระใช้ค้นด้วยวันที่หรือเลขอ้างอิง
- รายงานใช้สรุปตามบริการและช่วงเวลา
- Audit ใช้ตรวจผู้กระทำ เวลา และเป้าหมาย
- ใน production ต้องเปลี่ยนเป็น immutable event log และ export ที่ตรวจสอบลายเซ็น/chain ได้

## 9. ข้อจำกัดของ Prototype

- Refresh หน้าเว็บแล้วข้อมูลที่แก้จะหาย
- Login, OCR, LINE และ QR เป็นข้อมูลสาธิต
- ยังไม่มี PostgreSQL/API transaction จริง
- ยังไม่มี malware scan, backup, disaster recovery, MFA และ bank reconciliation
- ห้ามใช้รับชำระเงินจริงหรือออกเอกสารทางบัญชีจนกว่างาน P0/UAT จะผ่าน
